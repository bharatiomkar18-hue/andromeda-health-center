Calculation Rationale

Every metric on the Dashboard tab, defined exactly as computed. This is the same logic implemented in code — nothing here is simplified or approximate.

1. Scope & data preparation

Deduplication — rows are grouped by AWB No (trimmed to a string); within each group, only the row with the latest modified timestamp is kept. Rows with a blank AWB No are dropped and counted separately.

Pickup-pending exclusion — any shipment with a blank Network Arrival Date (i.e. not yet actually picked up) is removed entirely before any other calculation runs. These are never counted anywhere, not even as a separate bucket.

Date parsing — handles mixed formats in the same column (24-hour text, 12-hour AM/PM text, native Excel serial numbers, and verbose text like "August 4, 2026, 2:52 PM") without assuming a single fixed format.

"DSE" throughout this dashboard means Delivery Slot End Timestamp — the customer's promise date. Every breach, percentage, and filter is measured against it.

2. Delivery outcome classification

Checked in this exact priority order, first match wins:

  1. Delivered Date present → Delivered
  2. else Rejected present → Rejected (a resolved, terminal outcome — the customer refused delivery, it is not left as "still pending")
  3. else Status is "Cancelled" → Cancelled
  4. else Status is "Declared Lost" or "Loss Recovered" → Lost / Recovered
  5. else → Pending / In-Progress

Reference clock — for a Terminal outcome (anything except Pending), the shipment's own modified timestamp is used to judge lateness. For a still-Pending shipment, the current time ("now") is used instead, so an overdue-but-open shipment correctly shows as an open breach rather than being silently ignored.

3. FM / MM / LM breach cascade

Guiding principle: a shipment only counts as breached if it genuinely failed to be resolved to the customer by DSE. Root-cause attribution (FM/MM/LM) only happens after that is established. Missing an internal deadline is not, by itself, a customer-facing failure — a team gets full credit for recovering.

Evaluated in this exact order, first match wins:

  1. No Delivery Slot End Timestamp at all → "No Promise Date Generated" (excluded from every breach % denominator)
  2. Reached LM on/before DSE and delivered/rejected on/before DSE → On Time
  3. Has not reached LM yet, and DSE has not passed either → On Time (not yet due — not judged prematurely)
  4. Reached LM on/before DSE, but never delivered or rejected → LM breach
  5. Genuinely failed to reach LM in time and the FM lane deadline was missed → FM breach
  6. Genuinely failed to reach LM in time and the FM lane deadline was not missed (or the lane isn't in the cutoff table) → MM breach
The "provision" (step 2 vs. steps 5/6): if a shipment reached LM on/before DSE, everything that happens after that is entirely LM's responsibility — regardless of whether FM was individually late getting it there. FM/MM are only ever evaluated when the shipment genuinely never reached LM in time. A shipment that missed its own FM lane deadline but still made it to LM before DSE, and was delivered on time, counts as 100% On Time — this is deliberate, to give credit for recovery rather than double-punishing an ultimately successful delivery.
Why "delivered or rejected" and not "attempted": an out-for-delivery dispatch or a failed attempt alone is not enough to avoid an LM breach — the customer still did not get a resolution. Only an actual delivery or a customer rejection counts as compliant.
Lane table is exclusive, no fallback: only the 41 lanes in the cutoff table below are ever evaluated for an FM breach. A shipment on any other FM→LM lane pair gets no FM verdict at all — if it fails to reach LM in time, it is attributed to MM by default, since there is no lane-specific deadline to hold FM accountable to.

Reconciliation guarantee: FM Breaches + MM Breaches + LM Breaches always sums exactly to Overall Breaches, for the whole dataset and for every filtered slice. This is a mathematical property of the cascade above (each shipment lands in exactly one bucket), not a separately-maintained total.

4. Lane cutoff table (41 lanes)

Each lane (FM Territory → LM Territory) has a fixed daily line-haul departure cutoff time-of-day. Given a shipment's actual pickup timestamp, its FM deadline is the next occurrence of that cutoff on/after pickup. City-name aliases: BANGALORE→BENGALURU, DELHI→DELHI NCR.

5. AOT% / DOT% / ROT% / DSR% / FDDS%

AOT% (Attempted On Time) — the earliest of Delivered Date, First Out On Road Date, and First Attempt Date falls on/before DSE. Measures whether any LM action happened on time, regardless of outcome.
DOT% (Delivered On Time) — Delivered Date is on/before DSE. Strict: no grace day, no credit for a late-but-eventual delivery.
ROT% (Rejected On Time) — Rejected date is on/before DSE. Same strictness as DOT%.
DOT+ROT% — the union of the two above (delivered or rejected on/before DSE).
DSR% (Delivery Success Rate) — Delivered Date is present at all, with no time constraint against DSE. Answers "did it ever get delivered," independent of timing.
FDDS% (First Delivery Done Success) — Delivered, with Forward Attempted Count equal to 0 (zero prior failed attempts). Shown as a percentage of total shipments in scope.

6. Valid LM% / Invalid LM% (Fraud Attempt classification)

This is a sub-split of the LM Breach bucket only — it answers, for shipments already attributed to LM, whether the delivery attempt behind that breach was genuine or fraudulent, using the Fraud Attempt Report.

Per-attempt-row classification, checked in this order:

  1. con_at_distance_m > 70,000 → Valid, tagged "Customer Issue" (an implausible GPS distance is treated as a data/GPS issue, not fraud)
  2. fraud_status is "Genuine" → Valid
  3. fraud_status is "Address Issue" → Valid (an address problem is not a fraudulent attempt)
  4. fraud_status is "Fake - OR/AT under 30 min" or "Fake - AT under 500 m" and distance < 1,000m → Valid ("Genuine, distance override" — a small on-ground distance suggests the fake flag was a false positive)
  5. anything else containing "fake" → Invalid
Per-shipment rule — only the most recent attempt decides: a shipment's attempt rows are sorted by at_time; only the chronologically latest attempt's classification is used. Earlier attempts on the same tracking ID are superseded, not aggregated or OR'd together — a later Invalid attempt overrides an earlier Valid one, and vice versa.
No matching fraud-report record at all → defaults to Valid (benefit of the doubt: no evidence of a fraudulent attempt exists for that AWB). This guarantees Valid LM% + Invalid LM% always exactly equals LM Breach% at any level of filtering — there is no third "unassessed" bucket.

7. RM mapping

Hub names are matched between the main report's LM Station Name and the RM Mapping file's FACILITY NAME after normalizing both (uppercase, hyphens/underscores/spaces collapsed to a single underscore) — this tolerates naming variants like SW-NAG-Rahul-Nagar-AD vs. SW_NAG_Rahul_Nagar_AD. Re-uploading an updated RM Mapping file fully replaces the current mapping (last upload wins) — useful for a hub addition or an RM reassignment.

8. Data handling

All parsing and computation happens locally in this browser tab. Nothing is uploaded to any server. The password gates on each upload button are a basic access control for this file, not encryption — anyone with the file itself can read the password from its source code.
